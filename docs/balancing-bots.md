# balancing-bots.md — Боты стратегий для проверки баланса

> **Статус:** черновой концепт с сессии обсуждения (2026-08-13), написан **до** реализации по прямой
> просьбе пользователя. Ничего из этого не реализовано. Контекст и целевая функция `X(t)`, которую
> эти боты проверяют, — `production-balance.md`, прочитать сначала его.

## Зачем нужны боты, а не только аналитика

`X(t)` (идеальный зал, `production-balance.md` §4) — это потолок при нулевом трении: обмен по
себестоимости, ноль ошибок, эталонный темп вложений. Реальная игра трётся об переговорные надбавки,
разный аппетит к риску, разное распределение усилий по времени — и это принципиально не считается
формулой, потому что зависит от решений, а не только от структуры цепочки. Единственный способ понять,
насколько сильно и по-разному реальные стратегии отклоняются от `X(t)`, — прогнать сильно разные,
но правдоподобные стратегии через `BalancingHarness` много раз и посмотреть на результат.

## Что уже есть (фундамент, не переписывать заново)

`SimpleBot` (`Game.Bots`) уже реализует одну конкретную стратегию — по факту это фиксированная точка
в пространстве, которое описано ниже (максимальный леверидж, весь темп сразу с первого хода, см. §2):
берёт стартовый кредит на максимум, с первого хода объявляет вложение в исследование поколений на
потолок (`MaxCommitmentPerTurn`), строит все уже разблокированные фабрики сектора, продаёт остаток
системе, обслуживает капремонт не раньше двух самых дешёвых (намеренно невыгодных) ступеней. Не делает
сейчас: никогда не вызывает `SetRndCommitment` (R&D конкретной фабрики не растёт вообще, только
командная разблокировка поколений) и никогда не вызывает `RepayLoan` (долг просто копится). Это не
баг существующего кода — `SimpleBot` не претендовал на разнообразие стратегий, это его первая и
единственная точка. Задача ниже — не переписать его, а параметризовать: `SimpleBot` в текущем виде
станет одной из ячеек сетки (leverage≈1, profile≈0, см. §2), а не отдельным классом.

`BalancingHarness.RunMany` (`Game.Engine.Tests`/аналог в `Game.Balancing`) уже прогоняет N партий и
усредняет метрики по ходам — сетка стратегий добавляется как внешний цикл поверх него (по одной ячейке
сетки — свой вызов `RunMany`), не требует переписывать сам харнесс.

## 1. Пробел, который нужно закрыть до сетки стратегий

Независимо от профиля стратегии, боту нужно уметь то, чего `SimpleBot` сейчас не делает вовсе:

- **R&D конкретной фабрики** (`SetRndCommitment`) — без этого уровень/скорость отдельной фабрики
  никогда не растёт, только сам факт разблокировки следующего передела командой. Нужно решение
  «сколько вкладывать в R&D уже построенной фабрики», не только «сколько в командное поколение».
- **Возврат долга** (`RepayLoan`) — сейчас взятый кредит никогда не гасится добровольно, только
  обязательным процентом от долга за ход (`MandatoryRepaymentRatePerTurn`). Без добровольного
  погашения ось «leverage» ниже вырождается — низкий leverage должен означать не только «меньше брать»,
  но и «активно отдавать», иначе разница между leverage=0 и leverage=1 видна только в момент старта,
  а не на протяжении всей партии.
- **Обмен между ботами за пределами одной жёстко заданной пары.** Сейчас `TrySignSimpleContract` —
  не переговоры, а один фиксированный контракт между двумя заранее заданными ботами одного сектора на
  один-единственный финальный материал сектора. Реальные кросс-секторные зависимости
  (`production-chains.md`: А→Д обогащённые редкие металлы, Б→Д текстолит, В→А/Б тара и упаковка и
  т.д.) требуют, чтобы бот мог найти контрагента и сойтись в цене для *любого* материала, нужного ему
  на входе, а не только продать один финальный продукт заранее назначенному партнёру. Без этого сетка
  ничего не проверит на партии из нескольких секторов — кросс-секторные материалы просто не потекут
  между ветками, весь смысл «команды вынуждены торговать друг с другом» (SPEC §1) у ботов не
  воспроизведётся. Это не про третью ось стратегии (§2 ниже) — это базовая работоспособность сетки в
  принципе, нужна при любых `leverage`/`profile`.

### Упрощённый биржевой стакан (набросок, не решено)

Не полноценные переговоры — это по-прежнему прерогатива живых людей, ядро замысла игры (SPEC §1:
«точные расчёты — серверу; переговоры, доверие, союзы — людям»). Ботам нужен механический способ
находить друг друга и сходиться в цене без диалога:

- Каждый ход (или раз в несколько ходов) каждый бот выставляет заявки по материалам своего рецепта:
  **заявка на покупку** — материал, объём дефицита на входе, цена не выше некоторого порога (например,
  себестоимость следующего передела минус целевая маржа); **заявка на продажу** — материал, объём
  излишка сверх уже законтрактованного, цена не ниже порога (себестоимость производства плюс
  минимальная маржа).
- Простой матчинг — не в движке (движку, как и сейчас, всё равно, человек это или бот с бланком), а в
  мозге бота, `Game.Bots`: заявки на покупку по убыванию цены, на продажу — по возрастанию, сведение
  первых совпадающих пар через уже существующие `SubmitContractProposals`/`ConfirmContract` — тем же
  путём, что и сейчас `TrySignSimpleContract`, просто для многих пар контрагентов и многих материалов
  вместо одной жёстко заданной связки.
- Не нашёлся контрагент — не простой производства, а откат на уже существующий предохранитель:
  аварийную закупку у системы (SPEC §5.3), она для этого и задумана.
- Открыто (см. §4): как часто пересчитывать стакан за один ход решений, и что происходит с
  непокрытыми заявками — сгорают или переносятся на следующий цикл матчинга.

## 2. Пространство стратегий — две независимые оси

Изначальная мысль пользователя («минимум кредита + быстрый органический рост» vs «много кредита +
разгон R&D + первым получить уникальный товар») на самом деле смешивает два разных измерения: сколько
риска берёт команда (кредитное плечо) и как она распределяет усилия по времени (когда именно
вкладывается). Это разные оси — можно быть агрессивным по кредиту, но всё равно вкладывать ровно, а
не рывками; можно быть консервативным по кредиту, но всё равно распределять усилия неравномерно.
Разводим на две независимые параметризованные оси, каждая — число от 0 до 1:

### Ось `leverage` (0..1) — аппетит к риску/кредиту

- `0` — почти без добровольного кредита: не берёт кредит сверх стартового минимума, гасит долг
  (`RepayLoan`) при первой возможности, когда свободный кэш превышает буфер на ближайший ход
  (зарплата + содержание + плановый R&D), развивается на марже от продаж.
- `1` — берёт кредит на максимум доступного при первой возможности, реинвестирует немедленно, не
  спешит с добровольным погашением (платит только обязательный минимум), приоритет — вложение в
  потолок `MaxCommitmentPerTurn` (и командного, и фабричного R&D) над скоростью обслуживания долга.
- Промежуточные значения — линейная интерполяция доли доступного кредита/темпа погашения между этими
  полюсами (конкретная формула — деталь реализации, не эта сессия обсуждения).

### Ось `profile` (0..1) — распределение усилий по времени

- `0` — фронт-лоадед: с первого хода вкладывает по максимуму (как сейчас `SimpleBot`), к середине
  партии выходит на плато, вторую половину — консолидация и продажа, а не рывок вглубь.
- `1` — бэк-лоадед: первую половину партии держит скромный, дешёвый в обслуживании набор фабрик,
  копит кэш, вторую половину — резкий рывок вложений в глубину цепочки (в терминах исходной идеи
  пользователя — «кто-то долго качает первые переделы, но потом очень долго вкачивает последние»,
  наоборот тоже валидная точка на этой же оси).
- Промежуточные значения — момент переключения темпа сдвигается линейно по времени партии.

### Сетка прогонов

Декартово произведение `leverage × profile`, например 5×5 = 25 ячеек, в каждой — `N` партий с разными
зерном жеребьёвки (как сейчас делает `Program.cs` с `sessionCount`). `SimpleBot` в его нынешнем виде —
одна конкретная ячейка (`leverage≈1`, `profile≈0`), не удаляется и не заменяется — параметризованная
версия при `leverage=1, profile=0` должна вести себя как он сейчас (регрессионный ориентир при
реализации).

**Осознанно не входит в сетку как отдельная ось v1:** сама жадность/агрессивность заявок стакана
(насколько близко к себестоимости продавать, насколько щедро покупать) — общая для всех ячеек сетки
политика, не варьируется по `leverage`/`profile`. Сам обмен между ботами (стакан, §1 выше) при этом —
не опция, а обязательное условие: без него сетка вообще ничего не проверит на многосекторной партии,
кросс-секторные материалы просто не потекут между ветками. Если после первых прогонов окажется, что
жадность стакана сама по себе доминирует над `leverage`/`profile` — расширять сетку третьей осью
отдельным заходом, не смешивать с этим v1.

## 3. Метрики харнесса — что добавить к `BalancingReport`

Сейчас `BalancingReport`/`TurnsByIndex` считает по ходам: среднюю денежную массу, объём продаж
системе, состояние фабрик, долю дефолтов, разброс итоговых счетов между партиями. Этого достаточно
для проверки «не улетает ли денежная масса», но не для проверки сходимости к `X(t)`. Нужно добавить:

- **Эффективность по времени, на команду:** `Score(t) / X(t)` — требует `X(t)` как вход прогона
  (результат идеального зала, `production-balance.md` §4), не только сам по себе прогон ботов.
  `Score(t)` уже есть (`FinalScoreCalculator`, вызывается в произвольный момент, не только в конце
  сессии).
- **Итоговая сходимость между ветками:** разброс `Score(T)/X(T)` между ветками специализации в одной
  партии — должен быть узким (это и есть числовая проверка «во всех областях примерно одинаково» из
  исходной идеи пользователя).
- **Тепловая карта по сетке:** средний `Score(T)/X(T)` по каждой ячейке `(leverage, profile)`,
  усреднённый по партиям этой ячейки — показывает, есть ли доминирующая стратегия (клетка сильно выше
  остальных) или мёртвая зона (клетка систематически проваливается).
- **Траектория по времени для дебрифа:** `Score(t)/X(t)` как временной ряд на каждый профиль — не
  критерий прохождения/провала, а материал для отчёта и для визуализации самой идеи выпуклости (та же
  логика, что уже применяется к денежной массе — CSV с рядом по ходам, `Program.cs`).

## 4. Открытые вопросы

- Точная формула интерполяции `leverage`/`profile` между полюсами 0 и 1 — деталь реализации, не решена
  здесь намеренно (это код, не концепция).
- Как часто пересчитывать биржевой стакан за один ход решений, и что происходит с непокрытыми
  заявками (сгорают / переносятся на следующий цикл матчинга) — §1.
- Нужна ли жадность стакана как третья ось сетки сразу, или после первых прогонов на двух осях — см.
  §2. Не путать с самим стаканом (§1) — тот нужен в любом случае, вопрос только про то, варьировать ли
  его агрессивность по сетке.
- `X(t)` идеального зала (`production-balance.md`) должен быть реализован раньше или можно временно
  подставлять грубую заглушку (например, `X(t)` = экстраполяция текущей `MarginMultiplierByProcessingLevel`
  без реального решения совместной системы), чтобы начать прогонять сетку раньше — не решено.
