# Старт новой сессии по игровым ботам

Обновлено 20 октября 2026 года после явной остановки файлового опыта пользователем.
Это главный вход для новой сессии. Код игры в этом обновлении не менялся.

## Первые действия

Прочитать `AGENTS.md`, этот документ и [ASSISTANT-BOT.md](ASSISTANT-BOT.md).
Проверить `git status`, текущую ветку и последние коммиты.
Рабочая ветка называется `experiment/jev-bots`, репозиторий находится по адресу
`https://github.com/yafarkin/ImProd2`.

Пользователь остановил опыт и попросил подготовить контекст. Новый игровой запуск
или продолжение не разрешены этим запросом. До новой игры нужно согласовать
бюджет и горизонт. Остаток прошлого лимита не считать разрешением продолжать.
Серверы сейчас не требуется проверять. Автоматически запускать модели не нужно.

## Бюджет и ограничения учёта

Пользователь выбрал 8000 токенов игрового обмена и не больше десяти ходов.
Токенизатор `o200k_base`, пакет `tiktoken==0.14.0`.

| Состав | Токены |
|---|---:|
| Десять выданных запросов | 5775 |
| Девять ответов | 1278 |
| Всего | 7053 |
| Остаток исходного предела | 947 |

Учитываются точные сохранённые тексты JSON. Полная стоимость сессии Codex,
повторное использование её контекста, внутренние вычисления, инструменты,
написание кода и документов в эти числа не входят. Агент не видел точный
общий биллинг. Нельзя называть 7053 расходом всей сессии или обещать жёсткий
предел стоимости Codex по этому счётчику.

`exchange.py show` записывает расход перед выводом запроса и резервирует 500
токенов на ответ. `answer` проверяет размер, увеличивает расход и создаёт
маркер SHA-256. Повторная выдача того же запроса запрещена.
Пределы 8000, 500 и 10 пока заданы в Python-инструменте, а предел десяти ходов
проверяется ещё и C#-обёрткой. Произвольные новые лимиты пока не настраиваются
единым файлом. Не обещать такую возможность без изменения кода и тестов.

## Как устроен файловый опыт

`FileBotExperiment.cs` сохраняет компактное состояние и ожидает файл ответа.
`FileBotProtocol.cs` передаёт команды существующему `BotCommandExecutor`.
Все изменения игры идут через журнал `GameSession`.

Агент сам выбирал пакеты команд. Другой моделью или `SimpleBot` его решения
не заменялись. Он видел исходники и предыдущие результаты, поэтому проверка
не была слепым сравнением интеллекта моделей.

Псевдонимы `f1`, `f2` соответствуют только текущему запросу и строятся по ID фабрик.
Их нельзя угадывать по порядку типов в каталоге.
`new:TYPE` указывает на последнюю успешно построенную фабрику этого типа
в текущем пакете. Это позволяет построить и назначить рабочих одним ответом.
Такой возможности не было у старого чат-бота с сырыми ID.

## Проверка и предпочтения

На момент последнего изменения кода проходили 154 теста C# и три теста счётчика.
Консоль собиралась без предупреждений. В текущем обновлении меняются документы
и состав архива, игровые тесты повторно запускать не требуется.

Пользователь предпочитает один небольшой блок за раз, работу в отдельной ветке,
коммит и push результата. При длинном автоматическом прогоне он попросил
проверять состояние раз в пять минут. Для управляемой агентом игры читать состояние
всё равно нужно перед каждым решением; это активная игра, а не фоновый мониторинг.
Не запускать новые эксперименты из запроса только на обновление документов.
