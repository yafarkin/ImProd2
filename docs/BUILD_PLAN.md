# BUILD_PLAN.md — Пошаговый план разработки

> Как пользоваться: подавай LLM **по одному блоку за раз**. Каждый блок самодостаточен, имеет чёткий вход, выход и критерий готовности. Не давай следующий блок, пока текущий не доведён до рабочего + протестированного состояния. Это защита от того, чтобы вывалить всё ТЗ разом и получить сырую кашу.
>
> Читать вместе с `../AGENTS.md` (правила работы) и `SPEC.md` (что строить).

---

## Общая логика порядка

Строим **изнутри наружу**: сначала ядро, которое можно проверить без интерфейса (домен → движок → конфиг → хранение), потом боты для симуляции баланса, и только потом UI по ролям. Причина: если сначала делать экраны, баланс и движок останутся непроверенными до самого пилота; а если сначала ядро — его можно гонять тестами и ботами задолго до первого живого прогона.

```
Фаза 0: Каркас решения
Фаза 1: Доменное ядро (сущности + правила, без движка)
Фаза 2: Конфигурация (GameConfig как данные)
Фаза 3: Event sourcing (журнал + восстановление)
Фаза 4: Тактовый движок (расчёт тика)
Фаза 5: Контракты (жизненный цикл)
Фаза 6: Рынок и экономика (внешняя экономика, репутация)
Фаза 7: Боты и симуляция (калибровка баланса)
Фаза 8: Каркас Web (Blazor, аутентификация, real-time)
Фаза 9: Экраны по ролям
Фаза 10: Аналитика, полировка, подготовка к пилоту
```

Внутри фаз — пронумерованные блоки. Ниже каждый блок: **вход → задача → выход → готово когда**.

## Фаза 1 — Доменное ядро

> Цель фазы: описать сущности и базовые правила как чистый код без движка, БД и времени. Всё — состояние экземпляра, никакой статики.

### Блок 1.1 — Базовые сущности справочника
- **Вход:** SPEC §5, §8; терминология AGENTS §5.
- **Задача:** `Sector`, `Material`, `Recipe` (входные материалы + выход + скорость), `FactoryDefinition`. Это неизменяемые справочные данные (позже придут из конфига). Пока — просто типы + фабричные методы для тестов.
- **Выход:** типы справочника + тесты на конструирование рецепта и разложение «материал → прямые входы».
- **Готово когда:** можно собрать простую цепочку (руда → лист → гвоздь) в коде и тест это подтверждает.

### Блок 1.2 — Команда, фабрика, склад
- **Вход:** SPEC §5.6, §5.7; блок 1.1.
- **Задача:** `Team`, `Factory` (тип, рабочие, выбранный продукт, уровень, вложения в R&D), `Warehouse`/`MaterialOnStock`. Инварианты (рабочих ≥ 0, склад не отрицательный). Ограничение «фабрики только своего сектора» (SPEC §5.2).
- **Выход:** сущности + тесты на инварианты и на запрет чужого сектора.
- **Готово когда:** нельзя создать фабрику вне сектора команды; склад ведёт себя корректно.

### Блок 1.3 — Расчёт себестоимости и пирамиды
- **Вход:** SPEC §9.3 (пирамида входов), §5.4 (маржа по переделу); блок 1.1.
- **Задача:** рекурсивный расчёт себестоимости материала и полной развёртки входов до сырья («сколько руды в одном гвозде»). Чистая функция над справочником. Числа — из заглушки конфига, помечены как некалиброванные.
- **Выход:** функция + тесты на многоуровневой цепочке.
- **Готово когда:** для трёхуровневой цепочки функция возвращает верную развёртку и себестоимость.

## Фаза 2 — Конфигурация

### Блок 2.1 — Модель GameConfig
- **Вход:** SPEC §16 (список параметров), §5, §8; AGENTS §3 (конфиг = данные).
- **Задача:** POCO-модель всего конфига: секторы, материалы, рецепты, определения фабрик, стартовые параметры, тайминги/пресеты, экономические параметры (заглушки), библиотека новостей (структура), флаги MVP (налоги/депозиты вкл-выкл). Всё числовое — с пометкой «требует калибровки».
- **Выход:** модель конфига + пример `gameconfig.pilot.json` (заглушечные значения).
- **Готово когда:** пример конфига десериализуется в модель без потерь.

### Блок 2.2 — Загрузка и валидация конфига
- **Вход:** блок 2.1.
- **Задача:** загрузчик JSON (System.Text.Json) + валидатор (ссылочная целостность: рецепты ссылаются на существующие материалы; каждый материал приписан сектору; нет циклов в цепочке производства кроме допустимых кросс-секторных; флагманы разрешимы). Внятные ошибки.
- **Выход:** загрузчик + валидатор + тесты (валидный конфиг проходит, битые — с понятной ошибкой).
- **Готово когда:** подсунутый битый конфиг даёт осмысленное сообщение, валидный — грузится.

## Фаза 3 — Event sourcing

> Здесь закладывается «блокчейн»-журнал и восстановление. Всё последующее изменение состояния идёт только через него.

### Блок 3.1 — Событие и журнал с хеш-цепочкой
- **Вход:** SPEC §4 (event sourcing), §11; AGENTS §2 (правила 5, 6).
- **Задача:** базовый тип события (`Change`), интерфейс применения к состоянию, `EventLog` с append-only и хеш-цепочкой (SHA-256 от сериализованного события + хеш предыдущего). Применение состояния и запись — атомарно (нельзя изменить состояние в обход журнала). Сериализация — System.Text.Json.
- **Выход:** механизм событий + журнал + тесты (цепочка хешей ломается при подмене записи; порядок сохраняется).
- **Готово когда:** тест на целостность цепочки проходит; подмена события детектируется.

### Блок 3.2 — Снапшоты и восстановление
- **Вход:** блок 3.1; SPEC §11 (восстановление после сбоя).
- **Задача:** durable запись журнала на диск, периодические снапшоты, восстановление состояния = загрузка снапшота + доигрывание хвоста журнала. Детерминизм (AGENTS правило 6).
- **Выход:** persistence + тест «упали и восстановились»: состояние после восстановления идентично.
- **Готово когда:** прогон N событий → снапшот → ещё события → «перезапуск» → идентичное состояние.

## Фаза 4 — Тактовый движок

### Блок 4.1 — Сессия и фазы хода
- **Вход:** SPEC §4; блоки 1.x, 3.x.
- **Задача:** `GameSession` (держит всё состояние, не статика), модель трёх фаз, таймер фаз с управлением ведущего (продлить/ускорить/пауза — как события), read-only окно, серверное игровое время. Жеребьёвка хода окончания на старте (в журнал).
- **Выход:** конечный автомат фаз + тесты (переходы, read-only блокирует действия, окончание в диапазоне).
- **Готово когда:** фазы переключаются детерминированно; действия в read-only отклоняются.

### Блок 4.2 — Производство (расчёт одного тика, часть 1)
- **Вход:** SPEC §4 (порядок расчёта), §5.6 (производительность); блоки 1.x, 4.1.
- **Задача:** производственная часть расчёта тика: производительность от рабочих (линейно/убывающая отдача из конфига), деление мощности между продуктами, списание входов и зачисление выхода, обработка нехватки входов. Всё — через события.
- **Выход:** шаг производства + тесты (полная/частичная/нулевая обеспеченность входами).
- **Готово когда:** на фикстуре из цепочки выпуск и списание считаются верно и детерминированно.

### Блок 4.3 — Финансы тика (часть 2)
- **Вход:** SPEC §5.1, §5.6, §5.9, §5.10; блок 4.2.
- **Задача:** зарплаты, плата за наём/увольнение, проценты по кредитам, принудительный кредит при нехватке, (опц.) налоги и депозиты, R&D-вложения и переходы уровней. Порядок — по SPEC §4.
- **Выход:** финансовый шаг + тесты (нехватка денег → принудительный кредит; R&D копится и открывает уровень).
- **Готово когда:** баланс команды меняется согласованно; принудительный кредит срабатывает по правилу.

### Блок 4.4 — Сборка полного тика
- **Вход:** блоки 4.1-4.3.
- **Задача:** оркестрация полного тика в фиксированном порядке (SPEC §4), фиксация состояния, инкремент дня. Пока без контрактов и рынка (заглушки).
- **Выход:** полный проход тика + интеграционный тест на несколько ходов.
- **Готово когда:** сессия проходит N ходов детерминированно, состояние восстановимо из журнала.

## Фаза 5 — Контракты

### Блок 5.1 — Модель контракта и жизненный цикл
- **Вход:** SPEC §6.
- **Задача:** `Contract` (spot/recurring, на уровне команда+продукт), `DeliveryEvent`, статусы, неизменяемость после подписания. Логика заключения: независимый ввод двумя сторонами → сверка → код подтверждения → подтверждение управляющим. Обработка несовпадения (статус «конфликт»).
- **Выход:** модель + переходы статусов + тесты (совпало/не совпало, подтвердить может только управляющий).
- **Готово когда:** нельзя подтвердить неуправляющим; несовпадение даёт «конфликт».

### Блок 5.2 — Исполнение контрактов в тике
- **Вход:** блок 5.1; SPEC §4, §6; интеграция в блок 4.4.
- **Задача:** шаг исполнения контрактов в расчёте тика: поставки по recurring/spot, Delivery Miss (штраф, репутация), Termination (штраф выше), mutual/voluntary расторжение, пересмотр через предложение. Аварийная закупка у системы (SPEC §5.3).
- **Выход:** шаг исполнения + тесты (пропуск поставки, срыв контракта, расторжение по согласию без штрафа).
- **Готово когда:** все ветки несоблюдения считаются верно; аварийная закупка работает как потолок цены.

## Фаза 6 — Рынок и экономика

### Блок 6.1 — Внешняя экономика (цена + ёмкость)
- **Вход:** SPEC §5.4, §5.5.
- **Задача:** функция состояния экономики: по тренду сессии выдаёт на каждый тик (цена, ёмкость) по каждому материалу; продажа сверх ёмкости — с понижающим коэффициентом; множитель маржи по переделу; электричество как системный ресурс. Тренд — из сценария конфига.
- **Выход:** рыночный шаг + тесты (подъём/спад двигают цену и ёмкость; перепроизводство обваливает цену).
- **Готово когда:** продажа в пределах и сверх ёмкости считается по правилу; тренд влияет предсказуемо.

### Блок 6.2 — Репутация
- **Вход:** SPEC §7; данные из DeliveryEvent (блок 5.x).
- **Задача:** расчёт публичной репутации (% с затуханием, период полураспада из конфига), пристрелочные первые ходы, отдача «процент + количество».
- **Выход:** репутационный модуль + тесты (свежий срыв весит больше; восстановление со временем; пристрелочные не бьют).
- **Готово когда:** динамика репутации соответствует правилам затухания и «прощения».

### Блок 6.3 — Новостная лента
- **Вход:** SPEC §5.4, §13.
- **Задача:** привязка «тренд → пул заголовков», выбор без повторов в пределах сессии, ручное событие ведущего как тот же механизм.
- **Выход:** генератор новостей + тесты (нет повторов; ручное событие вклинивается).
- **Готово когда:** лента выдаёт корректные по тренду заголовки без повторов.

## Фаза 7 — Боты и симуляция

### Блок 7.1 — Простые боты
- **Вход:** всё ядро (фазы 1-6); AGENTS правило 6 (детерминизм).
- **Задача:** боты с базовыми стратегиями (строят добычу, простые контракты, продают системе) для автопрогонов без UI.
- **Выход:** боты + прогон полной партии ботами end-to-end.
- **Готово когда:** партия из 8 ботов проходит полную сессию без вмешательства.

### Блок 7.2 — Харнесс балансировки
- **Вход:** блок 7.1.
- **Задача:** прогон многих партий, сбор метрик (денежная масса по ходам, throughput, доля дефолтов, разброс итоговых счётов), вывод для калибровки конфига.
- **Выход:** инструмент симуляции + отчёт по прогону.
- **Готово когда:** можно прогнать N партий и получить таблицу метрик; виден график денежной массы (проверка на неконтролируемый рост).

## Памятка по ведению работы

- После каждого блока LLM даёт: что сделано, какие файлы, что покрыто тестами, что осталось открытым.
- Если блок вскрыл нерешённый вопрос из SPEC §16 — обозначить развилку, предложить вариант, **не** расширять объём блока.
- Числа — всегда из конфига-заглушки с пометкой «требует калибровки». Реальная калибровка — в фазе 7.
- Не сливать соседние блоки «за компанию». Один блок = один заход.
