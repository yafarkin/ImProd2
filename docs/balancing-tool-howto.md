# balancing-tool-howto.md — Как пользоваться утилитой балансировки

> **Статус:** рабочая инструкция, Блок 7.3.7 (`BUILD_PLAN.md`), последняя часть плана из
> `docs/production-balance.md`/`docs/balancing-bots.md`/`docs/production-staging.md` — эти три
> документа объясняют **зачем** и **как задуман** метод, этот — **как запустить руками** и **что
> означают числа на выходе**. Написан в расчёте на то, что вы открыли этот файл без всякой памяти о
> проекте — может быть, через 5-7 лет, может быть, вас просто попросили «прогони калибровку». Ничего
> из контекста этого файла не требует чтения переписки, в которой он появился.

## Зачем это вообще

Игра построена вокруг производственных цепочек (`Samples/production-models/*.json`) — руда → прокат →
... → готовый автомобиль, и так на 4 сектора одновременно на «взрослых» файлах. Числа в этих файлах
(стоимость постройки фабрики, пороги исследований, цены сырья) — заглушки, подобранные на глаз, а не
прогонами. Если их не выверить, то либо один сектор оказывается сильно доходнее другого (несправедливо
для команд), либо цепочка вообще непроходима за отведённое время сессии, либо команды массово
проваливаются в принудительные займы. Эта утилита (`Game.Balancing`) считает, насколько всё плохо, и
даёт числа, по которым понятно, что именно поправить.

Она не играет за вас и не подбирает числа сама — она только измеряет.

## Два режима

### `--mode ideal-hall` — идеальный зал

Быстрый (секунды), детерминированный расчёт теоретического потолка X(t): сколько могла бы стоить
команда каждого сектора к ходу `t`, если бы играла вообще без ошибок. Не бот, не партия, случайности
нет — один и тот же конфиг всегда даёт один и тот же результат. Годится для первой, самой дешёвой
проверки: даже без единого бота уже видно, если один сектор в разы «слабее» другого просто по своим
цифрам конфига (себестоимость, маржа, стоимость постройки).

Подробнее про метод — `docs/production-balance.md` §4.

### `--mode grid` (по умолчанию) — сетка ботовых стратегий

Медленный (может идти часами на большой сетке) прогон настоящего игрового движка силами простых ботов
по сетке двух осей — `leverage` (аппетит к кредиту) и `profile` (когда именно вкладываться: сразу или
под конец). Каждая ячейка сетки — это N партий, усреднённых в одну сводку. Показывает, как реальная
(со всеми трениями движка — торговлей, износом, кредитом) игра отклоняется от идеального зала.

Подробнее про метод — `docs/balancing-bots.md`.

## Как запустить

Из корня репозитория:

```bash
# Идеальный зал на конкретном файле цепочки
dotnet run --project src/Game.Balancing -- --config src/Game.Config/Samples/production-models/metallurgy.json --mode ideal-hall

# Сетка ботов (долго!) на том же файле, поменьше для первой проверки
dotnet run --project src/Game.Balancing -- --config src/Game.Config/Samples/production-models/metallurgy.json --grid-steps 3 --sessions-per-cell 5

# Без --config вообще — короткий интерактивный список файлов Samples/production-models/*.json
dotnet run --project src/Game.Balancing --
```

Или после `dotnet build`, тем же исполняемым файлом напрямую (быстрее — без пересборки при каждом
запуске): `src/Game.Balancing/bin/Debug/net8.0/Game.Balancing` (или `.dll` через `dotnet`), с теми же
флагами после имени файла (без `--`).

### Флаги

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--config <путь>` | нет (интерактивный список) | Файл цепочки — либо голая production-model (`Samples/production-models/*.json`), либо уже собранный целиком `GameConfig` (например `Samples/gameconfig.pilot.json`). Тип определяется автоматически по содержимому файла. |
| `--session <путь>` | `Samples/sessions/pilot.json`, только если `--config` — голая production-model | Файл сессионных параметров (экономика, пороги R&D, длительность и т.д.) в паре с `--config`. Не нужен, если `--config` уже полный `GameConfig`. |
| `--preset <id>` | `short` | Какой `SessionPresets` из сессионного файла использовать (`short`/`medium`/`full` в стандартных файлах). |
| `--mode <grid\|ideal-hall>` | `grid` | Режим — см. выше. |
| `--grid-steps <n>` | `5` | Сетка `n×n` по `leverage`/`profile` (равномерно от 0 до 1). Только для `--mode grid`. |
| `--sessions-per-cell <n>` | `5` | Партий на одну ячейку сетки. Только для `--mode grid`. |
| `--teams-per-sector <n>` | `2` | Команд-ботов на каждый сектор конфига (секторов — от 1 на стадии 1 до 4 на стадии 4, см. `docs/production-staging.md`). |
| `--maintain-factories <true\|false>` | `true` | Заказывают ли боты капремонт вовремя (`false` — «пренебрегающий» вариант, специально чтобы проверить, что фиксированной декларации без обслуживания рано или поздно не хватает). |
| `--out <путь>` | `balancing-report.json` | Куда писать JSON-отчёт. |

**Первый прогон нового файла — маленький.** `--grid-steps 3 --sessions-per-cell 3` займёт секунды-минуты
и уже покажет, стоит ли вообще гонять полную сетку (`--grid-steps 5` и выше, `--sessions-per-cell` в
десятках) — та может идти часами, это нормально и ожидаемо, инструмент рассчитан именно на это (в
консоли идёт периодический heartbeat — строка вида `[00:03:12] ячейка 7/25 ... — партия 12/20` — не
полный лог, просто чтобы было видно, что процесс жив).

## Рабочий цикл

Один вызов утилиты — **один файл цепочки целиком**, не подмножество: если в файле 4 сектора, все
четыре считаются в одной партии разом (так проверяется и обмен между ними, не только каждый сектор
сам по себе). Цикл калибровки одного файла:

1. `--mode ideal-hall` на файле — самая дешёвая проверка. Если X(T) уже сильно разъезжается между
   секторами на идеальном зале (без единого бота) — чинить нужно сначала это, сетка ботов только
   унаследует и усилит проблему.
2. `--mode grid`, сначала маленькая сетка (см. выше) — смотрим на `Grid.Cells[].OverallAverageFinalConvergence`
   и `AverageFinalConvergenceBySector` (глоссарий ниже).
3. Правим конфиг (какой параметр — см. глоссарий), повторяем шаг 1-2 **того же файла**, пока не
   устроит.
4. Переходим к следующему файлу лестницы стадий (`metallurgy.json` → `metallurgy-petrochemistry.json`
   → `...-forestry.json` → `...-forestry-electronics.json`, `docs/production-staging.md`). Стадии не
   калибруются параллельно — числа стадии 1 используются как якорь для более широких файлов (тот же
   приём, что уже применялся в `production-staging.md`, «Согласование заглушек»).

## Как читать JSON-отчёт

Отчёт (`BalancingRunReport`) — один файл, три раздела: `Metadata`, `IdealHall`, `Grid` (только в режиме
сетки). Без единой трассы отдельных ходов/действий ботов — только цифры.

### `Metadata`

Кто/когда/чем считал: путь конфига и сессии, режим, пресет, `MaxTurns` (сколько ходов посчитан
идеальный зал — публично известная верхняя граница пресета, не тайный розыгрыш конца партии), список
секторов, git-коммит репозитория на момент прогона, время в UTC. Пригодится, когда сравниваете два
отчёта «до» и «после» правки — по `GitCommit`/`ConfigPath` видно, что именно изменилось между ними.

### `IdealHall.ValueByTurnBySector`

X(t) по каждому сектору, по ходам (индекс 0 — ход 1). Это ряд денег — теоретический потолок стоимости
команды сектора на этот ход, если играть без ошибок (`docs/production-balance.md` §3-4).

- **Сравнивайте секторы только на последнем ходу (конец ряда), не в середине.** Разная форма кривой
  посередине — нормально (одна ветка может идти ровнее, другая — рывком под конец), сравнивать имеет
  смысл только итог.
- **Ряд может начинаться отрицательным** — эталонная политика вкладывает в R&D/исследование поколений
  сразу на потолок у всех фабрик разом, окупается не сразу (`docs/production-balance.md`,
  «дорогой старт»). Это не баг, если ряд к концу выходит в заметный плюс.
- **Если ряд НЕ выходит в плюс к последнему ходу вовсе** — сектор в принципе не окупается на этом числе
  ходов даже в идеальных условиях. Крутить: снизить `Rnd.MaxCommitmentPerTurn`/`GenerationResearch.MaxCommitmentPerTurn`
  этого сектора (эталон вкладывает меньше — дешевле старт), или поднять `Economy.BaseMarketPerMaterial`/
  `MarginMultiplierByProcessingLevel` для его материалов (выше выручка), или снизить `FactoryDefinitionConfig.BuildCost`/
  `FixedCostPerTurn` его фабрик.
- **Если один сектор к концу заметно выше/ниже остальных** — структурный перекос конфига этого сектора
  относительно других, никакая игра ботов тут ни при чём (это идеальный зал, ботов ещё не было). Тот же
  набор рычагов, что абзацем выше, но здесь цель не «выйти в плюс», а «сравняться с соседями». Не
  правьте материалы точечно — используйте единый коэффициент на весь хребет цепочки сектора (тот же
  приём, что `docs/production-staging.md`, «Согласование заглушек между стадиями»: домножить все
  `BuildCost`/`FixedCostPerTurn`/пороги `GenerationResearch`/`Rnd` сектора на одно число, чтобы
  внутренняя ценовая шкала сектора относительно самого себя не разъехалась). Для системной цены вдоль
  цепочки есть готовый инструмент — `SystemSalePriceLadderCalculator`/`/admin/price-ladder` в
  `Game.Web` — пересчитывает `BasePrice` вниз по цепочке от одного параметра роста, не приходится
  редактировать вручную.

### `Grid` (только `--mode grid`)

`GridSteps`/`SessionsPerCell`/`TeamsPerSector` — параметры самого прогона (для контекста). `Cells` —
список ячеек сетки, по одной на `(leverage, profile)`:

| Поле | Что означает | Высокое/плохое значение → куда смотреть |
|---|---|---|
| `ForcedLoanShare` | Доля команд-ходов, закончившихся принудительным (штрафным) займом — прокси «дефолта». | Стабильно высокая **на всех** ячейках сетки (не только на `leverage=0`, «консервативных») — деньгам не хватает независимо от стратегии: `StartingConditions.MaxStartingLoanAmount` слишком мал, `WorkerProductivity.SalaryPerWorkerPerTurn`/`FactoryDefinitionConfig.FixedCostPerTurn` слишком велики относительно выручки, или `StartingConditions.MandatoryRepaymentRatePerTurn` слишком агрессивен. |
| `ForcedRepairEventShare` | Доля команд-ходов, где фабрика ушла в вынужденный простой по износу. | Высокая — `Wear.BaseWearRatePerTurn`/`AccelerationFactorPerTurn` слишком быстрые для длины сессии, или `Wear.CriticalConditionThreshold`/стоимость `OverhaulTiers` не оставляют команде реального шанса успеть с капремонтом. |
| `AverageFinalScoreSpread` | Средний разброс (максимум минус минимум) итоговых счетов команд партии, в деньгах. | Само по себе мало о чём говорит без сравнения с масштабом экономики — если число сопоставимо с самим итоговым счётом, смотрите `AverageFinalConvergenceBySector` за причиной (по секторам или по случайности партии). |
| `OverallAverageFinalConvergence` | Score(T)/X(T), усреднённая по всем командам и партиям ячейки — «на сколько реальная игра в этой ячейке недотягивает до идеала». Тепловая карта — сравнивайте это число между ячейками сетки. | Заметно ниже 1 (или отрицательное) на **всех** ячейках сразу — реальный движок (торговля, износ, кредит) съедает намного больше, чем идеальный зал предполагал; начните с `ForcedLoanShare`/`ForcedRepairEventShare` той же ячейки — часто причина в них. Заметно ниже именно у `leverage≈0` (все) — консервативная стратегия слишком дорого платит за осторожность (обгоняет ли её вообще `leverage≈1`? если нет — leverage не так важен, как задумывалось). |
| `AverageFinalConvergenceSpread` | Средний разброс Score(T)/X(T) между **секторами** внутри одной партии этой ячейки. Должен быть узким у откалиброванной цепочки. | Широкий — см. `AverageFinalConvergenceBySector` этой же ячейки, чтобы понять, какой именно сектор отстаёт, и правьте его конфиг (тот же набор рычагов, что у `IdealHall` выше). |
| `AverageFinalConvergenceBySector` | То же Score(T)/X(T), но по каждому сектору отдельно, усреднённое по партиям ячейки. | **Главное поле для «какая ветка систематически отстаёт».** Сектор с числом заметно ниже остальных — тот, чей конфиг надо чинить в первую очередь. |
| `ConvergenceByTurn` | Score(t)/X(t), усреднённая по партиям ячейки, по ходам (индекс 0 — ход 1). `null` на ходах, где ни у одной партии не было содержательной сходимости (X(t) там ещё не вышел в плюс, см. `IdealHall` выше). | Форма ряда — растёт ли сходимость по ходу партии, или падает к концу (сектор «выдыхается»)? Падение к концу — часто признак того, что фабрики верхних уровней цепочки строятся слишком поздно относительно длины сессии: посмотрите `GenerationResearch.ResearchPointThresholdsByGeneration` — не слишком ли высокие пороги для отпущенного числа ходов. |

### `GenerationParity` (печатается всегда, при ≥ 2 секторах)

Добавлено 2026-08-15 (`docs/TODO.md` №2) — мгновенная, независимая от бота/сессии проверка: суммарная
«ценность» (`BaseCapacity × BasePrice × маржа`) материалов уровня 1..`StartingGeneration` по каждому
сектору, то есть то, что доступно боту с `leverage=0` (он никогда не инвестирует в исследование
поколений и навсегда остаётся на стартовом). Печатается в консоль **до** долгого прогона — если разрыв
между самым богатым и самым бедным сектором больше 1.5×, выводится явное предупреждение. Один и тот же
баг такого рода был найден вручную на двух разных файлах подряд, прежде чем стал автоматической
проверкой (`docs/production-balance.md` §1, «Генерация-1») — не игнорируйте это предупреждение, чинить
тем же способом, что уже сделано на `metallurgy-petrochemistry.json`/`-forestry.json`: добавить
недостающему сектору столько же материалов уровня 1 (дешёвые тупиковые «побочные продукты» сырья), не
трогая уже откалиброванный магистральный маршрут цепочки.

## Известные ограничения (v1)

Не гонитесь за идеальной точностью чисел — метод сам по себе грубый инструмент, «жадный алгоритм, чтобы
быстро увидеть проблему», не точная оптимизация:

- Идеальный зал считает эталонной политикой «вкладывать в потолок каждый ход» — не настоящую
  оптимизацию распределения вложений по времени (`docs/production-balance.md` §7, открытый вопрос v2).
- Обмен между ветками в идеальном зале — по себестоимости, без переговорной надбавки; в реальной игре
  (и в сетке ботов) трение переговоров всегда добавляет разрыв сверху того, что тут посчитано. (Излишек,
  который не забрала ни одна соседняя ветка, с сессии 2026-08-15 продаётся системе по настоящей
  котировке с наценкой уровня передела — `docs/TODO.md` №2, «Разобрано в сессии 2026-08-15» — до этого
  такой излишек просто лежал на складе по плоской `BasePrice`, занижая X(t) веток с ветвистой цепочкой
  сильнее, чем линейных; если сравниваете отчёт до этой даты с новым, числа X(t) не сопоставимы
  напрямую, калибровку конфига под старые отчёты нужно пересчитать заново.)
- Стакан ботов (`SimpleBot`) — не переговоры живых людей, механическое сведение заявок; его жадность
  (`MinSellMarginRate`/`MaxBuyPremiumRate` и т.д.) одна и та же для всех ячеек сетки, не варьируется по
  `leverage`/`profile` (осознанно не входит в сетку v1, см. `docs/balancing-bots.md` §2).
- Числа калибровки (`Rnd.MaxCommitmentPerTurn` и т.п.) сами по себе — результат прогонов, не эта
  инструкция; она объясняет, куда смотреть и что крутить, а не даёт готовые значения.
