# SPEC.md — Техническое задание

Проект: **«Производственные цепочки»** — офлайн бизнес-симуляция для тимбилдинга и вузов.

> Это спецификация *что строить*. Как строить — `../AGENTS.md`. Пошаговый план — `BUILD_PLAN.md`. Концепция для людей — `CONCEPT.md`.
>
> **Важно о числах:** все числовые значения в этом документе (цены, коэффициенты, ставки, длительности) — иллюстративные заглушки, требующие калибровки. Они не обкатаны. Единственный источник значений в рантайме — `GameConfig`.

---

## 1. Обзор

6-8 команд по 2-3 человека в одном зале. Локальный Wi-Fi, сервер на Raspberry Pi, клиенты — смартфоны (браузер), большой экран (проектор). Команды строят производственные цепочки (сырьё → переделы → флагманский продукт), специализированы по секторам, вынуждены торговать друг с другом. Сервер считает экономику; переговоры и заключение контрактов происходят вживую (люди перемещаются по залу, фиксируют сделки на бумажных бланках).

**Ключевой принцип:** точные расчёты — серверу; переговоры, доверие, союзы — людям.

**Среда:** полностью офлайн, без внешних зависимостей. Время — серверное игровое.

---

## 2. Состав MVP (первый пилот)

**Включено:** 4 сектора (А металлургия, Б нефтегазохимия, В лес/агротекстиль, Г электроника), полные производственные цепочки, контракты между командами, репутация, рынок с внешней экономикой и новостной лентой, тактовый движок (3 фазы), аварийная закупка, инструменты ведущего, тренировочная игра.

**Исключено из MVP:** страхование сделок, премиум-рецепты флагманов, тяжёлая техника для добычи (связь металл↔топливо), режим replay, боты-симуляции (делаются сразу после базового UI, но не в первом контуре).

**Кандидаты к рассмотрению для MVP:** налоги (на имущество и с продаж), банковские депозиты. Могут быть отключены через конфиг.

## 3. Ролевая модель

| Роль | Права |
|---|---|
| **Управляющий** (1 на команду) | Всё: фабрики, склад, R&D, кредиты, финальное подтверждение сделок |
| **Переговорщик** (1-2 на команду) | Просмотр состояния, доска потребностей, подготовка черновиков сделок. Подтверждать сделки не может |
| **Оператор** | Подтверждение сделок по коду, сверка с бумажным бланком |
| **Ведущий (фасилитатор)** | Управление игрой, вмешательство в экономику, полный обзор всех команд |
| **Администратор** | Настройка сессии до игры, регистрация команд, загрузка конфига |
| **Большой экран** | Анонимный read-only режим |

- Аутентификация — QR-код / короткий код, привязанный к команде и роли. Без паролей и email (мероприятие офлайн).
- Роль в интерфейсе совпадает с ролью в зале: управляющий сидит на месте, переговорщики перемещаются.
- У управляющего в UI — заметный счётчик черновиков сделок, ожидающих подтверждения.

*Реализовано в Блоке 8.1:* `Game.Domain.ParticipantRole` — полная ролевая модель (Manager,
Negotiator, Operator, Facilitator, Administrator; «Большой экран» не входит — анонимный режим, без
идентичности). `ParticipantRegistration`/`ParticipantRegistered` — участник регистрируется под
коротким кодом входа (`ShortCode`, тот же формат, что и `ContractConfirmationCode`, — решение
открытого вопроса §16 «точный формат QR-аутентификации»: буквенно-цифровой код, рендер в QR-картинку
как изображение — отдельная, более дешёвая надстройка на будущее). Вход — куки-аутентификация
ASP.NET Core (`GameSession.RegisterParticipant`/`TryAuthenticate`), не завязанная на Blazor circuit
(см. §11). Настоящая регистрация команд и генерация кодов ведущим/администратором — по-прежнему
Блок 9.8; пока это временная заглушка (`/dev/codes`) с фиксированным составом из двух команд.

## 4. Тактовый движок (game tick engine)

**Три фазы хода:**
1. **Расчёт** — атомарно и сразу для всех.
2. **Решения** — команды корректируют производство, ведут переговоры, заключают контракты. Сделки можно заключать в любой момент, у контракта указывается ход вступления в силу и (опц.) срок.
3. **Завершение** — короткое окно, последние секунды — read-only, чтобы не было гонки «кто успел кликнуть последним».

**Порядок расчёта внутри тика** (детерминированный, фиксированный):
финансы (проценты, зарплаты, налоги) → производство снизу вверх по уровням → исполнение контрактов → обновление рынка (цены/ёмкости) → новости/тренды → фиксация состояния.

**Переход между фазами:** гибрид — таймер по умолчанию; ведущий может продлить, ускорить, поставить на паузу. Все три действия — события в журнале.

**Время:** единый источник — сервер. Обратный отсчёт транслируется клиентам (SignalR), не считается локально.

**Длительность:** пресеты в конфиге — короткий (~15-20 ходов, 2 ч), средний (~25-35, полдня), полный (~40-60, день).

**Окончание игры:** точный ход неизвестен игрокам. Задаётся диапазон [X, Y]; конкретный ход выбирается жеребьёвкой на старте и пишется в журнал (даже ведущий не может подыграть). На экране в этот период — «игра близится к завершению», без цифры. Это защита от «предательства в финале» (обесценивания репутации на последних ходах).

**Event sourcing:** каждое изменение состояния — событие, дописываемое в append-only журнал с хеш-цепочкой (SHA-256 от содержимого события + реальной метки времени + хеш предыдущей записи). Состояние не меняется в обход журнала и полностью восстанавливается воспроизведением. Критично для восстановления после сбоя на Raspberry Pi посреди сессии. Метка времени каждой записи — только для дебрифинга/аудита (§12) и разбора инцидентов; на игровую логику и детерминизм воспроизведения не влияет. Первая запись (начало сессии) несёт контент-хеш `GameConfig` — журнал привязан к своему конфигу: при восстановлении/дебрифе хеш сверяется с фактически поданным конфигом, и дрейф либо подмена конфига обнаруживаются.

## 5. Экономика

### 5.1. Стартовые условия
Команда получает только деньги — кредит свободной суммы под процент, растущий с размером займа. Фабрик нет, всё строится самостоятельно. UI на первом ходу должен явно вести («у вас нет фабрик, начните с добычи»).

### 5.2. Ограничение по сектору
Команда строит только фабрики своей ветки (жёстко). Дерево R&D — своё у каждого сектора. Следствие: у каждого материала ровно один производитель на зал → аварийная закупка становится основным предохранителем от монополии.

### 5.3. Аварийная закупка у системы
Доступна для всех материалов; включается/выключается администратором в настройках сессии (на пилоте — включена). Цена — множитель к текущей рыночной цене материала (не константа). Служит потолком монопольных цен. Переключение по ходу игры — событие в журнале.

### 5.4. Рынок и внешняя экономика
Функция состояния экономики на каждый ход выдаёт по каждому материалу **пару значений: цену и ёмкость** (сколько единиц система выкупит по этой цене; сверх — с понижающим коэффициентом). Обе величины растут в подъём и падают в спад. Экономика следует сценарному тренду (подъём/стабильность/спад), заданному на сессию; новостная лента публикует заголовки из библиотеки, соответствующие тренду. Продавать системе можно продукцию любого уровня цепочки.

Множитель маржи по уровню передела: продукция более высокого передела продаётся с большей наценкой (стимул подниматься вверх по цепочке). Значения — в конфиге.

*Реализовано в Блоке 6.1:* тренд — кусочно-постоянное изменение цены/ёмкости за ход, накопленное с первого хода включительно и общее для всех материалов (не проценты, абсолютные величины из конфига); вне заданных сценарием отрезков экономика не движется. Цена и ёмкость не уходят в минус. Ёмкость на ход общая для всех продавцов материала (не персональная квота команды) — расходуется по мере продаж и не восстанавливается до следующего обновления рынка; продажа сверх неё уходит по цене с понижающим коэффициентом, что и является механизмом «перепроизводство обваливает цену». Множитель маржи по умолчанию 1, если для уровня передела в конфиге нет отдельной записи — конфигурировать нужно только те уровни, что получают надбавку.

*Реализовано в Блоке 6.3:* новостная лента — тот же сценарный тренд, что двигает цену/ёмкость (ход вне всех отрезков сценария трактуется как «стабильность» и для новостей тоже); каждый тик после обновления рынка случайно подбирается ещё не прозвучавший в этой сессии заголовок из пула, соответствующего текущему тренду. Если пул для тренда исчерпан — новости в этот ход просто не будет, повтор силой не допускается. Ручное событие ведущего (SPEC §9.5, §13) публикует любой заголовок библиотеки тем же событием и тем же ограничением на повтор, но без привязки к текущему тренду — это осознанный сценарный инструмент ведущего, а не часть автоматики.

### 5.5. Электричество
Системный ресурс, не производится ни одной командой. Потребляется фабриками уровня 2 и выше. Цена — из функции экономики.

*Реализовано в Блоке 6.1:* цена электричества следует тому же тренду, что и цена материалов (общий сдвиг цены за ход), от своей базовой величины в конфиге. У электричества нет ёмкости — оно не продаётся системой, а потребляется командами; собственно потребление (кто и сколько платит за ход) сюда не входит и заведено как открытый вопрос — в `FactoryDefinitionConfig` пока нет поля расхода электричества на фабрику.

### 5.6. Фабрики
- **Постройка:** мгновенная (заплатил — работает со следующего хода).
- **Продажа:** системе за часть стоимости (ликвидационная цена).
- **Рабочие:** наём/увольнение мгновенные, но с разовой платой за действие. Производительность от числа рабочих — линейная до базовой численности, с убывающей отдачей сверх неё (кривая — в конфиге).
- Если фабрика производит несколько типов материала, мощность делится между ними.

*Реализовано в Блоке 7.1:* постройка (`GameSession.BuildFactory`), наём и увольнение
(`HireWorkers`/`FireWorkers`) — как проверяемые действия команды поверх журнала (изначально
планировались только к Блокам 9.1/9.2 вместе с UI, но понадобились уже простым ботам — без них
некому строить и нанимать рабочих). Стоимость постройки — новое поле
`FactoryDefinitionConfig.BuildCost`, заглушка, требует калибровки. Продажа фабрики системе
(ликвидационная цена) в это не входит — по-прежнему открытый вопрос (§16).

*Реализовано в Блоке 7.2:* доля от `BuildCost`, которую платит система при ликвидации, — новое
поле `FactoryDefinitionConfig.LiquidationValueCoefficient` (заглушка, требует калибровки). Само
действие «продать фабрику по ходу игры» по-прежнему не реализовано — коэффициент пока используется
только итоговым счётом (§5.11), где нужна оценка «сколько фабрика стоит при ликвидации» независимо
от того, продают ли её на самом деле.

### 5.7. Склад
Гибрид: бесплатный лимит вместимости + плата за превышение.

### 5.8. R&D
Два трека объединены в одну ось — уровень конкретной фабрики (у каждой фабрики свой, начинается с 1): накопленные вложения в эту фабрику двигают её по уровням, а сам уровень одновременно даёт эффективность (множитель к скорости производства) и *является* «новым уровнем производства» — отдельного механизма разблокировки поверх этого нет. Накопительные вложения по ходам, темп выбирает команда. Вложенное в конкретную фабрику не перенаправляется на другую (сохраняется цена ошибки) — это следует само собой из того, что вложение физически привязано к фабрике, а не к абстрактному общему пулу.

### 5.9. Кредиты и (опц.) депозиты
- Стартовый кредит — свободная сумма, ставка растёт с размером.
- Дополнительные займы — в любой момент; ставка зависит от закредитованности и репутации. В UI до подтверждения — расчёт платежа за ход.
- При невозможности платить — принудительный кредит под карательный процент (растёт с каждым таким займом; в кабинете, не на экране). Команда не выбывает никогда. Ставка принудительного займа заведомо хуже любого добровольного (иначе появится стратегия «не платить ради дешёвого капитала»).
- (Опц.) Депозиты под процент — применение свободным деньгам и эталонная ставка доходности.

*Реализовано в Блоке 4.3:* единая кривая ставки (база + рост от текущего размера долга) применяется и к стартовому, и к любому последующему займу; зависимость от репутации пока не учитывается — заводится вместе с самой репутацией (Блок 6.2). Штрафная надбавка принудительного займа копится на команде целиком и действует на весь её долг, а не только на принудительно взятую часть — упрощение, но гарантирующее ту же цель («хуже, чем было», а не только «хуже этого конкретного займа»).

*Реализовано в Блоке 6.2:* к той же кривой добавлена надбавка за репутацию — линейно от 0 при 100% публичной репутации команды до настроенного максимума при 0%. У команды без истории поставок репутация по умолчанию 100% (надбавка не действует), поэтому старт сессии не меняется. Действие пересчитывается заново на каждом ходу по репутации, накопленной строго до начала этого хода — собственные срывы/расторжения текущего хода не успевают повлиять на уже начисленную в его же начале ставку.

### 5.10. Налоги (опц. для MVP)
- Налог на имущество: % от стоимости фабрики за ход (наказывает простаивающие фабрики).
- Налог с продаж: % со сделки. Служит стоком денежной массы (противовес притоку от продаж системе). Ставки — в конфиге, обнуляемы.

### 5.11. Итоговый счёт
Всё по ликвидационной стоимости:
```
Счёт = Кэш − Долг + Склад (≈50% рыночной цены) + Фабрики (по цене продажи системе)
```
R&D не учитывается (расход, ценность уже проявилась в производстве). Логика: оценка фабрик по цене продажи делает безразличным «продать или держать» в конце — нет вырожденной гонки ликвидации. Объяснение игрокам: «в конце считаем, сколько вы стоите при ликвидации».

*Реализовано в Блоке 7.2:* `FinalScoreCalculator` — чистая функция, не привязанная к концу сессии
(можно звать в любой момент для отчёта/дебрифа): склад оценивается по текущей рыночной котировке
каждого материала × `EconomyConfig.WarehouseLiquidationRate` (новое поле, заглушка, ≈0.5); фабрики —
по `BuildCost × LiquidationValueCoefficient` их типа (§5.6). Результат несёт разбивку по слагаемым
(`Cash`/`Debt`/`WarehouseValue`/`FactoriesValue`/`Score`), а не только сумму. Используется харнессом
балансировки для метрики «разброс итоговых счётов».

## 6. Контракты

- **Типы:** spot (разовая поставка) / recurring (бессрочный, регулярные поставки).
- Заключается на уровне **команды и типа продукции**, не конкретной фабрики.
- **Заключение:** обе команды вводят условия независимо → система сверяет совпадение → генерирует код подтверждения → команды переносят условия и код на бумажный бланк → оператор сверяет и подтверждает по коду (данные вручную не вводит). Финальное подтверждение со стороны команды — только управляющий.
- **Условия:** объём, тип продукции, цена за единицу, штраф за срыв, ход вступления в силу, срок (для spot — момент поставки; для recurring — диапазон). Страхование — вне MVP.
- **Два уровня несоблюдения:**
  - *Delivery Miss* — пропуск конкретной поставки: штраф, удар по репутации, контракт продолжает действовать.
  - *Termination* — прекращение контракта целиком: существенно выше штраф и репутационный удар.
- **Расторжение mutual** (обоюдное) — без штрафов. **Voluntary** (одностороннее) — дорогое, барьер намеренно высокий; прекращает контракт целиком.
- **Пересмотр условий recurring** — только через предложение, вторая сторона вправе отклонить; при отказе контракт продолжает действовать без изменений и без штрафа за факт предложения.
- Контракт после подписания **неизменяем**; меняется только статус. Изменение условий = новый контракт взамен расторгнутого.
- Обработать несовпадение введённых условий: статус «конфликт» + подсказка, что разошлось.
- (Открыто) Лимит активных контрактов на команду.

## 7. Репутация

- Публичный % исполненных поставок **с затуханием** (свежие срывы весят больше; период полураспада — в конфиге). Затухание даёт возможность исправиться.
- Первые N ходов — «пристрелочные»: срывы не идут в публичную репутацию или с пониженным весом (учёт стартовой неразберихи, пока разбираются в правилах).
- Отображается % **вместе с количеством** поставок (оценка статистической значимости).
- Считается по отдельным поставкам (DeliveryEvent), не по контрактам.

*Реализовано в Блоке 6.2:* вес каждого факта — множитель тяжести × 0.5^(возраст в ходах / период полураспада), нулевой возраст даёт полный вес. Проценту исполнения дополнительно вносит вклад одностороннее (voluntary) расторжение контракта — второй, более тяжёлый уровень несоблюдения из §6, с настраиваемым множителем тяжести относительно обычного срыва; засчитывается только инициатору, а не обеим сторонам. Обоюдное (mutual) расторжение — не несоблюдение, на репутацию не влияет никак. «Пристрелочные» ходы выбраны как **полное исключение**, а не пониженный вес: срыв/расторжение в эти ходы не попадает ни в процент, ни в счётчик поставок для оценки значимости, как будто его не было; при этом успешные поставки в пристрелочные ходы засчитываются как обычно — прощается только неудача, а не сам факт раннего участия. У команды без единой поставки репутация по умолчанию 100% (нет свидетельств срыва). Публичная репутация используется и как вход в ставку по кредиту (§5.9).

**Уровни открытости данных:**
- *Публично на экране:* репутация, финансовый рейтинг, сводка доски потребностей.
- *Приватно всегда:* цены конкретных сделок, состав контрагентов, внутренние параметры производства (рабочие, уровень R&D), состояние принудительных кредитов.

## 8. Производственные цепочки

Полный граф материалов и фабрик по 4 секторам — в отдельном документе `production-chains.md` (см. приложение). Ключевые принципы:

- 4 сектора × 2 команды. Внутри сектора команды специализированы по-разному → торговля даже внутри сектора.
- Зависимости между секторами возникают на разных уровнях цепочки, не только в финале (цикличность, «камень-ножницы-бумага»).
- Сектор Г (электроника) — «связующая ткань»: зависит от материалов А и Б с уровня 2. **Проверить на пилоте, не слишком ли он уязвим.**
- Электричество — сквозной системный ресурс с уровня 2.

**Флагманы (по одному на сектор, симметричны):**

| Флагман | Сектор-владелец | Опорный сектор |
|---|---|---|
| Автомобиль | Металлургия (А) | Нефтехимия (Б) |
| Судно | Нефтехимия (Б) | Лес/текстиль (В) |
| Дом | Лес/текстиль (В) | Металлургия (А) |
| Вычислительный комплекс | Электроника (Г) | Металлургия (А) |

Право собрать флагман не закреплено — открытая гонка через R&D. Премиум-версии (с участием электроники) — вне MVP.

## 9. Интерфейсы

### 9.1. Большой экран
Один экран без ротации: рейтинг команд + таймер фазы + новости бегущей строкой + агрегированная сводка доски («активных объявлений: N · чаще всего ищут: …»).

### 9.2. Доска потребностей
Живёт в телефонах (вкладка, доступна всем), на большом экране — только сводка. Заполняется добровольно, содержимое не модерируется (недостоверность наказывается репутацией). Формат: структурированные поля (продукт, направление избыток/дефицит, грубый порядок объёма) + необязательный комментарий.

### 9.3. Экраны игрока (мобильный веб)
Дашборд команды (баланс, кредит, репутация, сводка производства, активные контракты, события); управление фабриками; склад (+ продажа системе); R&D; кредиты; контракты (список, черновик, подтверждение встречного ввода, предложения пересмотра/расторжения); доска потребностей; история/отчёты; новостная лента; отдельная облегчённая **переговорная панель** (что нужно, что можем предложить, наша репутация, черновик сделки).

Дашборд должен отвечать на три вопроса: что у меня плохо / что решить сейчас / что я обещал другим. Показывать себестоимость единицы и полную пирамиду входов продукта (обучающий инструмент).

### 9.4. Экран оператора
Очередь сделок; ввод/скан кода; сверка условий с бланком; подтверждение одним действием; отклонение с причиной.

### 9.5. Экраны ведущего (MVP)
Старт/пауза/продление фазы; обзор всех команд (полная видимость); грант отстающей команде; вкл/выкл аварийной закупки; **ручное событие экономики и корректировка цен**; алерты (близость к дефолту, неактивность команды).

### 9.6. Экраны администратора (до игры)
Настройка сессии (загрузка GameConfig); создание команд, распределение по секторам (автораспределение в наименее заполненный); регистрация игроков, генерация QR/кодов; чек-лист готовности перед стартом.

---

## 10. Тренировочный режим

Отдельная короткая тренировочная игра до основной (~8-10 ходов по минуте), те же команды и логины, но полностью независимое состояние и репутация. Служит и техническим прогоном (сеть, телефоны, оператор, бланки). **Следствие:** система поддерживает несколько сессий и быстрый сброс.

---

## 11. Нефункциональные требования

- **Производительность:** Raspberry Pi 4, ~25 одновременных клиентов, расчёт тика — заметно быстрее длительности фазы.
- **Офлайн:** без CDN, внешних шрифтов, NTP. Время — серверное игровое.
- **Устойчивость клиента:** Blazor Server circuit рвётся при блокировке телефона/уходе в фон — обязательна корректная обработка переподключения с восстановлением состояния.

  *Реализовано в Блоке 8.1:* личность участника живёт в куке ASP.NET Core (`CookieAuthenticationDefaults`),
  а не в состоянии circuit — обрыв и переподключение circuit никак не задевают аутентификацию: новый
  circuit читает ту же куку и сразу восстанавливает роль/команду, не спрашивая код заново. Плюс
  штатная реконнект-модалка `blazor.web.js` (шаблон .NET 8, не кастомный код).
- **Real-time:** SignalR для пуша (смена фаз, подтверждение сделок, новости, таймер).
- **Хранение:** durable append-only журнал + снапшоты на диск. System.Text.Json (не BinaryFormatter). SHA-256 (не MD5).
- **Восстановление после сбоя:** полное восстановление состояния из журнала.
- **Детерминизм:** одинаковый вход → одинаковый выход (условие ботов и тестов).
- **Приватность:** команды не видят чужие приватные данные даже при подборе URL.
- **Конфигурируемость:** все цепочки, коэффициенты, цены, тайминги, пресеты, тексты — в GameConfig (JSON), без перекомпиляции.

## 14. Тестирование и балансировка

- Юнит-тесты движка расчёта (детерминированность).
- **Режим симуляции ботами** — делается сразу после базового UI; прогон многих партий для калибровки коэффициентов и проверки денежной массы (риск неконтролируемого роста). До ботов страховка баланса — конфиг-параметры + ручная корректировка цен ведущим.

*Реализовано в Блоках 7.1-7.2:* простые боты (`Game.Bots`) и харнесс балансировки поверх них
(`BalancingHarness`) сделаны раньше UI — движок и конфиг были готовы к прогону без него. Харнесс
прогоняет N партий и сводит их в `BalancingReport`: денежная масса и throughput (объём продаж
системе) по ходам, усреднённые по партиям, доля дефолтов (принудительных займов на команду-ход —
своего понятия банкротства в игре нет) и средний разброс итоговых счётов между командами партии.
Консольный инструмент `Game.Balancing` печатает сводку и пишет CSV денежной массы по ходам — «виден
график» пока означает «можно построить в любой таблице», без отдельной инфраструктуры отрисовки.
- Нагрузочный тест на реальной Raspberry Pi.
- Пилотная игра с сокращённым сценарием — как этап проекта.

**Что проверить на пилоте:** уязвимость сектора Г; пропускная способность оператора при 8 командах; реальная длительность фаз; поведение денежной массы.

## 15. Наследие старого MVP

Существует прототип автора ~10-летней давности (проект IM.Production). Из него берётся **структура и идеи доменной логики** (change-паттерн с хеш-цепочкой журнала; двухуровневый R&D; идея разложения пирамиды себестоимости; идея налогов и депозитов; AmountPerDay как ось балансировки), но **не числовые значения** — они не обкатывались. Инфраструктура старого кода (статика для состояния, BinaryFormatter, MD5, привязка контрактов к фабрикам, лог в памяти) **не переносится** — заменяется решениями этого документа. Подробный разбор — в `tz-decisions.md`, раздел 12.

## 16. Открытые вопросы (свод)

**Формулы (значения — в конфиг, помечены как требующие калибровки):**
