# AGENTS.md

Руководство для LLM-агента, работающего над проектом **«Производственные цепочки»** (offline business simulation game).

> Этот файл описывает, *как* работать над проектом. Что именно строить — в `SPEC.md`. Пошаговый план сборки — в `BUILD_PLAN.md`. Концепция для людей — в `CONCEPT.md`.

---

## 1. Что это за проект (в двух абзацах)

Офлайн бизнес-симуляция для тимбилдинга и вузов. 6-8 команд по 2-3 человека в одном зале, локальный Wi-Fi, сервер на Raspberry Pi, клиенты — смартфоны, большой экран (проектор). Команды строят производственные цепочки (сырьё → переделы → флагманский продукт), специализированы по секторам и вынуждены торговать друг с другом. Расчёты берёт на себя сервер, переговоры и заключение контрактов остаются живыми (люди физически бегают по залу).

Технически: **.NET (последняя LTS), Blazor Server, event sourcing с хеш-цепочкой журнала, вся игровая конфигурация — данные (JSON), а не код.** Работает полностью офлайн, без внешних зависимостей.

---

## 2. Золотые правила

1. **Идём маленькими шагами.** Никогда не пытайся реализовать весь `SPEC.md` за один заход. Бери один блок из `BUILD_PLAN.md`, доводи до рабочего и протестированного состояния, останавливайся. Пользователь подаёт следующий блок сам.
2. **Домен — чистый, без инфраструктуры.** Доменный слой (сущности, правила, расчёт тика) не зависит от Blazor, БД, файлов, времени ОС. Никакой статики для игрового состояния (см. правило 4).
3. **Конфигурация — это данные.** Цепочки, коэффициенты, цены, тайминги, тексты новостей — всё грузится из JSON-конфига (`GameConfig`), ничего не зашивается в код. Если добавляешь игровую величину — она должна попадать в конфиг.
4. **Никакой статики для состояния.** Игровое состояние и справочные данные — это состояние экземпляра сессии (`GameSession`), не `static`. Это требование, а не пожелание: от него зависят параллельная тренировочная игра, боты-симуляции и тестируемость. (В старом MVP всё было статикой — так делать нельзя.)
5. **Всё меняется через журнал.** Любое изменение игрового состояния — это событие, дописываемое в append-only журнал с хеш-цепочкой (event sourcing). Состояние не должно меняться в обход журнала. Из журнала состояние должно полностью восстанавливаться.
6. **Детерминизм.** Один и тот же вход (конфиг + журнал событий) → одно и то же состояние. Никакой скрытой зависимости от `DateTime.Now`, случайности без явного seed, порядка перечисления словарей. Это условие работы ботов-симуляций и тестов.
7. **Тесты идут вместе с кодом блока, а не потом.** Каждый блок из `BUILD_PLAN.md` считается готовым, только когда покрыт тестами на свою логику.

## 3. Технологический стек

- **Бэкенд/домен:** C#, .NET (последняя LTS).
- **UI:** Blazor Server (один язык, состояние на сервере, SignalR из коробки, большой экран — просто ещё одна страница). **Важно:** circuit рвётся при блокировке телефона / уходе браузера в фон — обязательна корректная обработка переподключения с восстановлением состояния.
- **Хранение:** событийный журнал на диске (append-only) + снапшоты. Сериализация — System.Text.Json (НЕ BinaryFormatter). Хеш — SHA-256 (НЕ MD5).
- **Конфиг:** JSON (`GameConfig`), версионируемый.
- **Офлайн:** без CDN, внешних шрифтов, обращений к NTP. Время — только серверное игровое (game tick), не время ОС.

## 4. Структура решения (ориентир)

```
src/
  Game.Domain/         — сущности, value objects, правила, интерфейсы. Без зависимостей на инфраструктуру.
  Game.Engine/         — тактовый движок (расчёт тика), event sourcing, применение событий.
  Game.Config/         — модели GameConfig, загрузка и валидация JSON.
  Game.Persistence/    — durable журнал, снапшоты, восстановление.
  Game.Bots/           — боты для симуляции (появляется после базового UI).
  Game.Web/            — Blazor Server: страницы игрока, оператора, ведущего, админа, большого экрана.
tests/
  Game.Domain.Tests/
  Game.Engine.Tests/
  ...
config/
  gameconfig.pilot.json
docs/
  SPEC.md  CONCEPT.md  BUILD_PLAN.md  AGENTS.md
```

Точные имена не догма, но разделение «домен / движок / конфиг / хранение / веб / боты» соблюдай.

## 5. Терминология (единый язык)

Используй эти термины консистентно в коде и комментариях:

- **Session (GameSession)** — один прогон игры (тренировочный или основной). Держит всё состояние.
- **Tick / Day** — игровой ход. Состоит из трёх фаз: расчёт (calculation) → решения (decision) → завершение (closing, с read-only окном).
- **Sector** — отрасль (металлургия / нефтегазохимия / лес-агротекстиль / электроника).
- **Team (Customer в старом коде)** — команда игроков. В новом коде предпочитай **Team**.
- **Factory / FactoryDefinition** — фабрика команды / её описание-тип.
- **Material** — единица продукции (хранится, продаётся, поставляется).
- **Recipe** — правило преобразования (входные материалы + выход).
- **Contract** — сделка между командами (на уровне команды и типа продукции, НЕ конкретной фабрики). Типы: spot (разовый) / recurring (бессрочный).
- **DeliveryEvent** — отдельная поставка внутри контракта.
- **Reputation** — публичный % исполненных поставок с затуханием.
- **Market / EconomicState** — внешняя экономика: по каждому материалу выдаёт пару (цена, ёмкость) на текущий тик.
- **Change / Event** — атомарное изменение состояния, запись в журнал.

## 6. Что НЕ делать

- Не тащить формулы и числа из старого MVP как готовые — они **не обкатаны**. Старый код — источник идей и структуры, не значений. Все числовые параметры — в конфиг, помечены как требующие калибровки.
- Не использовать `static` для игрового состояния.
- Не менять состояние в обход журнала.
- Не завязываться на время ОС, неявную случайность, порядок словарей.
- Не добавлять внешние сетевые зависимости.
- Не реализовывать несколько блоков `BUILD_PLAN.md` за раз «пока пишу».
- Не хардкодить то, что должно быть в `GameConfig`.

---

## 7. Как отвечать пользователю

- Работаешь по одному блоку. В конце блока: краткое резюме что сделано, какие файлы созданы/изменены, что покрыто тестами, что осталось открытым.
- Если блок вскрыл вопрос, не решённый в `SPEC.md` — не выдумывай молча. Обозначь развилку и предложи вариант, но не разрастайся за пределы текущего блока.
- Спорные числовые значения бери из конфига-заглушки и явно помечай «требует калибровки».
